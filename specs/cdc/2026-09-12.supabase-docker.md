# Recette avec Supabase réel dans Docker — 12 septembre 2026

Statut : étape locale validée, CDC global encore incomplet. Aucun projet payant créé, aucune migration appliquée en production, aucun compte réel utilisé.

## Correction

Les fonctions `account-deletion` et `storage-cleanup` s’arrêtaient avant de traiter les requêtes : leur configuration imposait HTTPS, alors que le runtime Supabase local utilise `http://kong:8000`. Elles partagent maintenant un validateur d’adresse. HTTP nécessite une option explicite côté serveur et une origine locale autorisée ; les adresses avec identifiants, chemin, paramètres ou fragment sont rejetées. Un test de sécurité couvre l’absence d’option, les domaines voisins et les adresses étrangères.

## Huit scénarios d’intégration réussis

Exécution de `validation/supabase-local.test.mjs` : **9 tests Node réussis**, dont le test parent, aucun ignoré. Durée observée du premier parcours complet : environ 177 secondes. Le démarrage reproductible depuis une base vide passe également les huit scénarios (9 tests Node) en environ 164 secondes pour la phase HTTP, puis supprime les ressources de test. La suite générale passe **181 tests**.

1. Les véritables fonctions s’exécutent dans Edge Runtime. Le nettoyage refuse un appel sans son secret ; la suppression refuse les méthodes et origines non autorisées.
2. Trois comptes fictifs s’inscrivent via Auth, confirment les courriels capturés dans Mailpit puis obtiennent de vraies sessions. Trois identités sont présentes en base.
3. Le parcours initial minimal persiste le prénom et l’intention ; les pratiques sont sautées et aucune charge physiologique n’est inventée.
4. La reprise du même enregistrement retourne le même reçu. Un second JWT ne voit pas et ne peut pas modifier le Moment privé du premier compte. Durée 80 minutes et RPE null sont confirmés en PostgreSQL.
5. De vrais fichiers GPX et PNG sont téléversés. Le téléchargement restitue les mêmes octets. Un autre compte ne peut ni écrire dans le dossier privé ni obtenir son lien signé.
6. L’export est lu en pages de deux éléments. Les valeurs et chemins attendus sont présents ; l’autre JWT ne peut pas lire cet export.
7. Vault, `pg_cron` et `pg_net` déclenchent le worker réel. Après suppression d’une activité, les deux fichiers disparaissent de Storage et le téléchargement échoue. Le retour HTTP du job réel vaut 200.
8. La suppression de compte exige le mot de passe. Dès la demande, l’ancien JWT ne peut plus écrire ni téléverser. Les fichiers sont supprimés, puis Auth disparaît et le reçu devient `complete`. Une reprise retourne ce même état. Le refresh token est refusé. La participation et la photo de l’autre personne restent présentes et accessibles.

Versions observées : Docker Engine 29.7.2, Supabase CLI 2.117.0, PostgreSQL image 17.6.1.167, Auth 2.196.0, Storage 1.72.1, PostgREST 16.2, Edge Runtime 1.74.3 / Deno 2.1.4. Les services sont exposés uniquement sur `127.0.0.1`.

## Navigateur et restauration

Le navigateur utilise la vraie API locale. Connexion du compte confirmé, arrivée sur HOME avec son intention ouverte, ajout d’une Marche de `1:20`, souvenir seul et marquage du Moment. Après enregistrement, la journée affiche un seul Moment. Vérification SQL indépendante : 80 minutes, marquage vrai, souvenir exact, effort/défi/maîtrise null. Le formulaire n’a finalement transmis aucun fichier lors de l’essai du sélecteur : **le téléversement par navigateur n’est pas déclaré validé** ; les téléversements API décrits plus haut ont réussi.

Une sauvegarde complète du PostgreSQL fictif a été créée. Ses schémas `public`, `private`, `auth`, `storage`, `extensions` et `vault` ont été restaurés dans une base indépendante, avec leurs propriétaires et privilèges. Les 40 tables publiques présentes lors de cette première recette et leurs 90 lignes ont les mêmes empreintes après restauration. Les nombres d’identités et d’objets Storage correspondent. Les droits restaurés cachent toujours les activités de A à B ; A retrouve ses 80 minutes et son RPE null. Le catalogue global `collections`, absent de cette première fixture, est désormais ajouté au démarrage reproductible.

Les deux fichiers physiques du volume Storage ont été sauvegardés puis copiés dans un autre dossier : leurs empreintes correspondent. Il s’agit d’une restauration des schémas et d’un contrôle des fichiers, **pas d’un redémarrage complet d’Auth/Storage sur un second projet restauré**, ni d’une preuve de compatibilité avec une ancienne version du site. Les sauvegardes et identifiants fictifs restent privés et locaux.

## Intégration GitHub et limites restantes

Le workflow « Source and tests » exécute désormais la recette Docker avant la construction du site. La version de Supabase CLI et la révision de son action d’installation sont fixées. Le démarrage, le contrôle des ports, la préparation du schéma et les tests sont versionnés, avec arrêt au premier scénario d’intégration défaillant et destruction des volumes en CI. Voir `docs/engineering/LOCAL-SUPABASE.md`.

Le contrôle automatique d’approbation a refusé une extraction détaillée des définitions, droits et politiques de production, car elle pouvait contenir des informations sensibles. Les essais ont donc utilisé les références déjà présentes dans le dépôt ; la parité exacte avec le projet hébergé reste à établir.

Restent notamment : validation des octets des pièces jointes côté serveur et métadonnées des photos partagées, reprise des imports/téléversements dans le navigateur, matrice complète d’accessibilité et de performance, restauration complète et compatibilité de repli, cinq essais humains, puis déploiement et contrôle de l’URL publiée. Les 113 scénarios ne sont pas déclarés tous réussis ; le manifeste de livraison reste incomplet et bloque toujours Vercel.
